# 權限測試劇本(以示範模組驗證)

驗證對象:權限模型(ADR-0004)、查詢與判斷流程(ADR-0011)、資料範圍規則(ADR-0008)、移除所屬組織(ADR-0003)、管理範圍與可見範圍的分工(ADR-0005)、檔案儲存(ADR-0010)。模組與資料定義見 [示範模組1](../modules/demo.sub.sample-one.md)、[示範模組2](../modules/demo.sample-two.md)。

1. **wildcard 涵蓋未來(同層)**:角色勾示範模組1 的 `demo.sub.sample-one.*`(存單筆);下一版 seed 對示範模組1 新增權限 → 不改角色即擁有;對其編輯頁(`…edit-page`)新增的權限**不**自動擁有(子模組由自己的 `*` 代表)。
2. **資料範圍規則**:建規則「套用對象=客服角色 → 建立者 = 【操作者本人】」→ 客服查示範項目僅見自建;刪規則 → 恢復可見範圍。
3. **未宣告對照**:示範模組2 查詢僅受可見範圍保底(規則機制不介入)。
4. **頂層合成**:建兩條都命中同一人的規則,切換 OR/AND 驗結果集為聯集/交集。
5. **欄位級(綁父)**:無 `show-internal-note` → 詳情/編輯頁無此欄、API 投影排除;有 show 無 edit → 唯讀;硬送該欄寫入 → 拒。
6. **頁面自有權限**:無 `edit-page.show-history` → 編輯頁無歷程區塊,編輯功能不受影響(兩者獨立);`create-page.show-tips` 同理。
7. **路由防守**:角色未綁新增頁模組 → 手打網址被擋;綁了新增頁但無 `create` 權限 → 頁進得去、送出被 API 擋(頁與功能分離)。
8. **組織外**:授予示範模組1 的角色後移除所屬組織(radio 選保留)→ 三處列表標示、功能仍可用、資料範圍縮小。
9. **移除三檔**:dry-run 清單:(b) 只列該組織擁有 vs (c) 加列失去子樹支撐 — 用多所屬組織帳號驗差異。
10. **防越權**:矩陣只可勾操作者自身擁有的權限與模組。
11. **儲存雙路**:coverPath 公開 URL 直接顯示;attachmentPath 簽名下載,無 `view` 者 API 拒發。
12. **可見性開關**:ON→OFF 驗**業務資料**的名單與資料收縮、既有角色授予不動;治理頁(組織 / 使用者 / 角色)完全不動 — 見劇本 14。
13. **總覽也是模組**:角色未綁 `overview.*` → 登入後 `/` 轉到側欄第一個能進的頁(如 `/system/org-manager`),側欄沒有「總覽」列;手打 `/overview` 顯示無權限頁;綁回去 → 登入落在 `/overview`(ADR-0011「路由與導向規則」)。
14. **管理範圍 vs 可見範圍**(CONTEXT.md 兩個詞條;ADR-0005 的分工表):
    - **由角色決定、與所屬哪裡無關**:甲的所屬組織只有「南港店」,但持有一個擁有組織 = 租戶頂層的角色 → 組織管理頁的樹根是租戶頂層、整個租戶的組織與使用者都管得到;把角色換成擁有組織 = 南港店的那一個 → 樹根變成南港店,租戶頂層與其他分店**不出現**在樹上(不是灰的,是不回傳),`org(其他分店 id)` 回 `NOT_FOUND`。
    - **不受可見性開關影響**:把該租戶的開關設成 `own` → 上一條的結果完全不變(治理頁、角色候選、搬移候選都不動);同一個人去看業務模組(示範模組1)的清單則收縮成只剩所屬組織的資料 — 兩個範圍各管各的。
    - **多根**:同時授予擁有組織 = 南港店與 = 內湖店(兩者沒有共同上層)的兩個角色 → 組織樹有**兩個根**;停用其中一個角色 → 那一棵子樹整個退出管理範圍。
    - **無治理角色 = 空**:把全部角色解除(或全部停用)→ 沒有任何治理權限,治理頁進不去(`FORBIDDEN`);即使硬給 `view`,管理範圍也是空的、樹是空的。
    - **可見性開關的權限搬家**:租戶管理員(模板副本,含 `system.org-manager.*`)在編輯**自己租戶頂層**時看得到「使用者可見下層組織資料」開關並設得了;對**別的租戶**的頂層送出 → `NOT_FOUND`(管理範圍外);對非租戶頂層送出 → `VALIDATION_FAILED`;只持 `system.org-manager.view` 的人連開關都看不到、硬送 `FORBIDDEN`。
    - **搬移候選與租戶頂層保護**:候選 = 管理範圍 ∩ 同租戶 − 自己子樹;把租戶內的組織搬去別的租戶 → 範圍外即 `NOT_FOUND`(根組織看得到兩邊才會拿到 `CROSS_TENANT`),搬進自己的子樹 → `CYCLIC_MOVE`;租戶內的人搬租戶頂層本身 → `FORBIDDEN`。
15. **側欄商標繼承**(ADR-0010):租戶頂層設商標、下層不設 → 下層使用者的側欄顯示租戶的商標;下層自己設一張 → 改顯示自己的;把下層的清掉 → 又回到繼承來的那張(沿 `ancestors` 由近到遠找第一個有商標的上層)。
16. **租戶視角**:root 開通租戶(取消勾選示範群組)→ 租戶管理員登入:側欄無「模組與權限」「資料範圍」「示範群組」、組織樹以租戶頂層為根、沒有「開通租戶」按鈕;root 視角看得到新租戶並標「租戶」。
17. **擁有者保護**:租戶管理員試圖停用 / 移出租戶 / 解除自己(擁有者)的租戶管理員授予 → `OWNER_PROTECTED`;root 可執行;租戶內任何人對租戶頂層停用 / 刪除 / 搬移 → `FORBIDDEN`。

# 怎麼驗:每條劇本用哪一頁、哪個帳號、什麼步驟

第 5 段起兩支示範模組都有真頁面,17 條劇本**全部可以在畫面上跑完**(唯一的例外是劇本 1 的跨版本那半條,見該節)。本節取代 2026-09-20 的「第 4 段在 dev 可驗到哪裡」對照表。

## 驗收前的準備

### 三個帳號

| 代號        | 是誰                                                                       | 怎麼來                                                                                                                                                                                                                                                                                                                                         |
| ----------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **root**    | seed 的超級管理員(帳號 `root`,屬根組織;ADR-0002)                           | 部署時由 seed 建立,密碼在該環境的 Secret(`ROOT_ADMIN_*`,見 `docs/env-registry.md`)                                                                                                                                                                                                                                                             |
| **+tenant** | 租戶A 的首任租戶管理員 = **租戶擁有者**,持「預設角色」;所屬組織 = 租戶頂層 | root 在組織管理頁按「開通租戶」建出租戶A 與這個帳號(劇本 16 就是在驗這一步)。**密碼不是誰給的,是本人從啟用信的連結自己設的**(ADR-0009,7 天效期):dev / staging 的信會寄到 `MAIL_ALLOWLIST` 上的開發者信箱;**本機與 e2e 沒有 `RESEND_API_KEY`,api 自動改用記錄用 adapter,啟用連結直接印在 api 的 stdout**(`docs/env-registry.md`),從那裡複製即可 |
| **+user**   | 租戶A 底下一般使用者,所屬組織 = 南港店,持租戶自建的「客服」角色            | +tenant 在使用者管理頁建立,再於角色管理頁把「客服」指派給他                                                                                                                                                                                                                                                                                    |

### 組織與角色的前置

1. **root** 登入 → 組織管理 → 開通租戶,建「租戶A」與 **+tenant**(劇本 16 一併驗)。
2. **+tenant** 登入 → 組織管理 → 在租戶A 底下建「南港店」「內湖店」兩個分店。
3. **+tenant** → 使用者管理 → 建 **+user**(所屬組織:南港店);順手把 **+tenant 自己也加入南港店**(多一個所屬組織)——劇本 2 / 4 / 12 要兩個帳號的可見範圍有交集才比得出差異,劇本 9 的 dry-run 也要有一個多所屬組織的帳號。
   **「加進某個組織」自 #377 起有第二個入口**:組織管理 → 選「南港店」→「成員」分頁 →「加入成員」,一次可多選。兩個入口做的是同一件事(對每個人的所屬組織加一筆、寫同一筆 `user.add-org` 稽核),挑順手的用;**移出**只有使用者管理那一個入口。
4. **+tenant** → 角色管理 → 建「客服」角色(擁有組織 = 租戶A),權限矩陣勾示範家族(示範群組 → 示範次群組 → 示範模組1 與其三個隱藏頁、示範模組2 與其三個隱藏頁),各給 `view` / `create` / `edit` / `delete`;**先不要勾** `show-internal-note` / `edit-internal-note` / `show-tips` / `show-history`(劇本 5 / 6 會一項一項打開)。指派給 +user。

### 示範資料的兩個已知限制(會影響步驟,不是 bug)

- **seed 的 10 筆示範資料全部落在根組織**(`apps/db-migrator/seeds/demo-items.ts`;`orgs` 種子只有根組織一筆,租戶是開通出來的、各環境 id 不同,seed 引用不到)。所以 **+tenant / +user 一登入,兩支示範模組的列表都是空的** —— 那是對的,不是壞掉。凡是要比對「看得到 / 看不到」的劇本(2 / 3 / 4 / 8 / 12),**都要先用租戶帳號自己新增幾筆**。
- **seed 資料的建立者是固定的假 id**,所以 root 看 seed 那 10 筆時,詳情頁的「建立者」一律顯示「—」。要在畫面上看到人名,就自己新增一筆。

### 劇本 2 / 12 的共同前置資料

以下兩條劇本都要靠「同一個可見範圍裡、建立者與所屬組織都不同」的資料才驗得出來,**先照這個順序建**:

1. **+user**(當前組織 = 南港店)在示範模組1 新增 **2 筆**(名稱好認一點,例如「南港-自建1 / 2」)。
2. **+tenant** 把當前組織切到**南港店**,新增 **1 筆**(「南港-他人」)。
3. **+tenant** 把當前組織切回**租戶頂層**,新增 **1 筆**(「頂層-他人」)。
4. 示範模組2 也照樣各建一筆(劇本 3 的對照組要用)。

**分類欄的先決條件**:示範模組1 的分類下拉來自欄位管理的「示範分類」,`fieldCategories` / `fields` 兩個端點都掛在 **`system.field-manager.view`** 底下。**「客服」角色沒有這個權限**,所以 +user 會看到:**列表沒有分類篩選、表單的分類欄退成唯讀並說明原因**(原值保留)。這本身就是劇本 2 / 12 要一起確認的畫面;要讓 +user 選得了分類,就在角色矩陣另外給他欄位管理模組與 `view` 權限。

## 逐條劇本

### 劇本 1 — wildcard 涵蓋未來(同層)

- **用哪一頁**:角色管理 → 編輯「客服」→「權限設定」分頁(權限矩陣)
- **帳號**:+tenant
- **E2E**:`apps/e2e/src/specs/scenario-01-wildcard.spec.ts`(手動觸發,見下方「E2E 怎麼跑」)

1. 展開示範模組1 的節點,勾它的「全部(\*)」→ 同層的 view / create / edit / delete / 內部備註兩筆一起被連動勾起(M-03 / M-04)。
2. 往下看**編輯頁**節點:它的「全部(\*)」與 `show-history` **沒有**被勾起來。
3. 儲存、重新進入 → 勾選狀態一致。

**預期**:wildcard 只代表**該模組自己這一層**;子模組(隱藏頁)要各自勾自己的 `*`。資料庫只存一筆 `demo.sub.sample-one.*`(UI 看不到筆數,以 api 測試為準)。

**在畫面上驗不到的半條**:「下一版 seed 對示範模組1 新增權限 → 不改角色即擁有」要跨版本,由 api 測試覆蓋(`apps/api/src/demo-items-one/demo-items-one-permissions.test.ts`、`apps/api/src/permission/permission.test.ts`)。

### 劇本 2 — 資料範圍規則

- **用哪一頁**:「資料範圍」頁(建規則)+ 示範模組1 列表 / 詳情(看結果)
- **帳號**:規則用 **root**(資料範圍是根組織專屬模組,+tenant 的側欄沒有它 —— 見劇本 16);結果用 **+user**
- **前置**:上面「劇本 2 / 12 的共同前置資料」四筆
- **E2E**:`apps/e2e/src/specs/scenario-02-data-scope-rule.spec.ts`(手動觸發,見下方「E2E 怎麼跑」)

1. **+user** 先看一次示範模組1 列表:看得到自己 2 筆 +「南港-他人」(同在南港店的可見範圍內);「頂層-他人」看不到(+user 不屬租戶頂層)。列表**沒有分類篩選**,表單的分類欄**唯讀並說明原因**(沒有 `system.field-manager.view`)。
2. **root** → 資料範圍 → 左清單選「示範項目」(`demo_items_one`)→ 新增一條規則:**套用對象 = 指定角色「客服」**、過濾條件 **建立者 屬於【操作者本人】** → 儲存。
3. **+user** 重新整理列表。
4. 點進被濾掉那筆的詳情網址(`/demo/sub/sample-one/view-page/<id>`)。
5. **root** → 回資料範圍頁把規則刪掉 → 儲存。

**預期**:步驟 3 列表只剩 **+user 自己建的 2 筆**,`totalCount` 一併變小;步驟 4 顯示查無資料(api 回 `NOT_FOUND` —— 列表與單筆同一個答案,不透露存在與否);步驟 5 之後恢復成步驟 1 的三筆。root 自己不受影響(規則的套用對象是「客服」角色,而且超級管理員的可見範圍是全部)。

### 劇本 3 — 未宣告對照

- **用哪一頁**:「資料範圍」頁左清單(root)+ 示範模組2 列表(+user)
- **帳號**:root + +user
- **E2E**:`apps/e2e/src/specs/scenario-03-undeclared-target.spec.ts`(手動觸發,見下方「E2E 怎麼跑」)

1. **root** → 資料範圍頁 → 看左側的資料目標清單。
2. 維持劇本 2 的規則開啟狀態,**+user** 去看**示範模組2** 的列表。

**預期**:步驟 1 清單裡**只有「示範項目」**(`demo_items_one`),沒有 `demo_items_two` —— 示範模組2 的 seed 不宣告 `dataScopeTarget`。步驟 2 示範模組2 的列表**不受規則影響**,+user 照樣看得到別人在南港店建的那筆:沒有規則命中的資料目標,只剩可見範圍保底。

### 劇本 4 — 頂層合成 OR / AND

- **用哪一頁**:「資料範圍」頁(規則合成切換)+ 示範模組1 列表
- **帳號**:root 設規則、+user 看結果
- **前置**:把步驟 1 的四筆之一改成狀態「已發布」(其餘留「草稿」),讓兩條規則的結果集不相等
- **E2E**:`apps/e2e/src/specs/scenario-04-combine-op.spec.ts`(手動觸發,見下方「E2E 怎麼跑」)

1. **root** → 資料範圍 → 示範項目 → 建**兩條都會命中 +user** 的規則:①套用對象 = 指定角色「客服」→ 建立者 屬於【操作者本人】;②套用對象 = 指定組織「南港店」→ 狀態 屬於【已發布】。
2. 頂層合成切 **OR** → 儲存 → **+user** 看列表。
3. 頂層合成切 **AND** → 儲存 → **+user** 看列表。

**預期**:OR = 兩條的**聯集**(自建的 + 任何已發布的);AND = **交集**(自己建的且已發布的)。兩種情況下租戶隔離都仍在最外層 —— 別的租戶的資料永遠不會因為合成方式而冒出來。

> 套用對象比對的是操作者的**啟用中角色**與**所屬組織的直接關聯**,不是可見範圍也不是管理範圍:所以②要寫「南港店」(+user 的所屬組織),寫「租戶A」不會命中他。

### 劇本 5 — 欄位級權限(綁父模組)

- **用哪一頁**:示範模組1 的**詳情頁**與**編輯頁**
- **帳號**:+tenant 改角色矩陣、+user 看畫面
- **E2E**:`apps/e2e/src/specs/scenario-05-field-permission.spec.ts`(手動觸發,見下方「E2E 怎麼跑」)

1. 「客服」角色**兩筆內部備註權限都不給** → +user 看任一筆的詳情頁與編輯頁。
2. +tenant 只加 `show-internal-note` → +user 重新登入(或重整)後再看兩頁。
3. +tenant 再加 `edit-internal-note` → +user 再看編輯頁。
4. (選配,需要開發者工具)在步驟 1 的狀態下直接對 `updateDemoItemOne` 送出帶 `internalNote` 的 input。

**預期**:

- 步驟 1:詳情頁**沒有「內部備註」那一列**、編輯頁**沒有那個欄位**(不是顯示空值 —— api 根本不把這個欄位放進回傳物件)。
- 步驟 2:兩頁都看得到內容,編輯頁的欄位是**唯讀**並附說明。
- 步驟 3:欄位變成可編輯,存得下去。
- 步驟 4:`FORBIDDEN` + `extensions.reason = "FIELD_FORBIDDEN"`(欄位**一出現在 input 裡就要權限**,送 `null` 清空也一樣)。這一條由 api 測試覆蓋,畫面上不必硬驗。

**順手一起看**:在步驟 1 的狀態下給 `edit-page.show-history`,打開編輯頁的變更歷程 —— **內部備註在歷程裡一律顯示 `[redacted]`**,不會從側門外洩。列表的關鍵字搜尋也**不比對**內部備註(help 文案有寫)。

### 劇本 6 — 頁面自有權限

- **用哪一頁**:示範模組1 的**新增頁**與**編輯頁**
- **帳號**:+tenant 改矩陣、+user 看畫面

1. 不給 `create-page.show-tips` → +user 進新增頁:**沒有填寫提示區塊**,但名稱 / 分類 / 備註照樣填得了、存得下去。
2. 給 `show-tips` → 重進新增頁:標題下方多出提示區塊。
3. 不給 `edit-page.show-history` → +user 進編輯頁:**沒有變更歷程區塊**,但編輯與儲存完全正常。
4. 給 `show-history` → 重進編輯頁:表單底部多出歷程區塊,列出這筆的建立 / 編輯紀錄(新到舊)。

**預期**:**區塊與功能兩件事互相獨立** —— 少一個區塊不影響這一頁本來的 CRUD。兩筆權限分別綁在**新增頁**與**編輯頁**自己的模組上(不是綁列表頁),所以只在那一頁生效。

### 劇本 7 — 路由防守

- **用哪一頁**:示範模組1 的列表頁 + 直接在網址列打三種網址
- **帳號**:+tenant 改矩陣、+user 試網址
- **E2E**:`apps/e2e/src/specs/scenario-07-route-guard.spec.ts`(手動觸發,見下方「E2E 怎麼跑」)

1. 角色**不綁**新增頁模組(`demo.sub.sample-one.create-page`)→ +user 看列表:**沒有「新增」鈕**;手打 `/demo/sub/sample-one/create-page` → **無權限頁**。
2. 角色綁了新增頁模組、但**不給** `create` 權限 → 手打同一個網址:**頁進得去**,送出時被 api 擋(`FORBIDDEN`)。
3. 角色綁了詳情頁模組 → 手打 `/demo/sub/sample-one/view-page/<某筆 id>`:**進得去**,解出來的 id 就是要顯示的那一筆。
4. 手打 `/demo/sub/sample-one/whatever`(列表頁後面多接一段)→ **無權限頁**。

**預期**:**頁(模組)與功能(權限)是兩層,分開問**。步驟 3 / 4 的差別是「尾端動態參數的退路只對 hidden 模組成立」——詳情 / 編輯頁的模組路由本身不含識別碼,所以精準比對落空時**只對隱藏頁**再試一次「去掉最後一段」;link(列表頁)後面多一段仍然是打錯網址(ADR-0011「路由防守」、`apps/admin/src/lib/module-tree.ts` 的 `matchModuleRoute`)。

### 劇本 8 — 組織外

- **用哪一頁**:使用者管理(移除所屬組織)+ 角色管理「分配使用者」分頁 + 組織管理 + 示範模組1 列表
- **帳號**:+tenant 操作、+user 受影響
- **前置**:+user 只屬南港店;「客服」角色的擁有組織 = 租戶A;+user 在南港店已建過資料
  (把 +user 放進南港店可以走使用者管理的「選擇所屬組織」,也可以走組織管理 → 南港店 →「成員」分頁 →「加入成員」,#377;兩者等價)

1. +tenant → 使用者管理 → 把 +user 自「南港店」移除,確認彈窗的 radio 選 **「全部保留」**。
   (**移除只有這一個入口** —— 組織管理的「成員」分頁刻意不做移除,因為移除要跑 dry-run 三檔。)
2. 看三處列表:使用者管理、角色管理的「分配使用者」、指派角色的彈窗;順手到組織管理 → 南港店 →「成員」分頁確認 +user 已不在成員清單裡(#377)。
3. +user 重新登入 → 進示範模組1 列表。

**預期**:步驟 2 三處都把 +user 標成**「組織外」**;步驟 3 他**照樣進得去**示範模組1(角色授予還在、功能不受影響),但**看得到的資料收縮**(可見範圍少了南港店)。這正是「角色授予」與「所屬組織」兩件事分離的示範。

### 劇本 9 — 移除所屬組織的 dry-run 三檔

- **用哪一頁**:使用者管理 → 移除所屬組織的確認彈窗
- **帳號**:+tenant 操作;對象要是**多所屬組織**的帳號(前置第 3 步的 +tenant 自己,或另建一個同屬南港店 + 內湖店的帳號)

1. 對象同時屬南港店與內湖店,並持有兩個角色:一個擁有組織 = 南港店、一個擁有組織 = 租戶A。
2. 把他自南港店移除 → 看彈窗列出的 dry-run 清單。
3. 分別選三個 radio 再確認,比對結果。

**預期**:清單要分得出 **(b) 只列「該組織擁有的角色」** 與 **(c) 再加列「失去子樹支撐的角色」** 兩種範圍;(a) 全部保留則不解除任何授予。差異只有在多所屬組織 + 多角色時看得出來,單一組織的帳號驗不到。

### 劇本 10 — 防越權

- **用哪一頁**:角色管理 → 權限矩陣
- **帳號**:+tenant(**不是** root —— 超級管理員直接全權放行,看不出限制)

1. +tenant 新建或編輯一個角色 → 開權限矩陣。
2. 比對矩陣列出的模組 / 權限,與 +tenant 自己持有的(預設角色的內容)。
3. 打開租戶的**預設角色**看矩陣。

**預期**:矩陣**只列得出 +tenant 自己有的模組與權限**(顯示樹就是他的天花板);根組織專屬模組(模組與權限、資料範圍)根本不在樹上。預設角色是租戶的天花板,**只能縮不能擴**。

### 劇本 11 — 儲存雙路(公開封面 / 私有附件)

- **用哪一頁**:示範模組1 的新增 / 編輯頁(上傳)+ 詳情頁(顯示與下載)
- **帳號**:+user

1. 新增一筆,封面上傳一張 PNG / JPG / WebP(2MB 內),附件上傳一份 PDF 或 ZIP(20MB 內)。
2. 進詳情頁:封面**直接顯示**;複製圖片網址到無痕視窗開 → 仍然看得到(公開穩定 URL,不過期)。
3. 附件那一列按「下載」→ 這時才向 api 要一條**短效簽名網址**;把那條網址留著過一陣子再開。
4. 上傳一個不在白名單的檔型(例如 `.exe`)或超過上限的檔。
5. +tenant 把「客服」的 `view` 權限拿掉 → +user 再按下載。

**預期**:步驟 2 公開 bucket、步驟 3 私有 bucket(網址會過期);步驟 4 回 `UPLOAD_REJECTED`(訊息含 purpose);步驟 5 api **拒發**簽名網址(`FORBIDDEN`)—— 私有檔案的每一次取用都重新檢查權限,不是上傳當下檢查一次就算數。

### 劇本 12 — 可見性開關

- **用哪一頁**:組織管理 → 編輯**租戶頂層**的「使用者可見下層組織資料」開關;結果看示範模組1 列表與三個治理頁
- **帳號**:+tenant 切開關、+user 看結果
- **前置**:「劇本 2 / 12 的共同前置資料」四筆(+user 在南港店 2 筆、+tenant 在南港店 1 筆與租戶頂層 1 筆);**劇本 2 的資料範圍規則要先刪掉**,不然兩層收縮混在一起看不出是誰造成的

1. 開關 **ON**(可見下層)時,讓 **+tenant** 看示範模組1 列表 → 看得到租戶頂層那筆**與**南港店那三筆(他的可見範圍含下層)。
2. 把開關切成 **OFF**(`own`)→ +tenant 重新登入後再看列表。
3. 同一個狀態下,+tenant 去看**組織管理 / 使用者管理 / 角色管理**三個治理頁。
4. 順手確認 **+user** 的畫面:列表**沒有分類篩選**、表單分類欄**唯讀並說明原因**(分類選項掛在 `system.field-manager.view` 底下,「客服」沒有那個權限)。

**預期**:步驟 2 **業務資料收縮**成只剩自己所屬組織(租戶頂層)那筆;步驟 3 三個治理頁**完全不動**(樹根、使用者名單、角色候選都一樣)—— 治理模組看的是**管理範圍**,不看可見性開關(ADR-0005;細節見劇本 14)。既有的角色授予也不會因為切開關而變動。步驟 4 的兩個現象是「選項來源掛在別的模組權限底下」的正常結果,不是壞掉。

### 劇本 13 — 總覽也是模組

- **用哪一頁**:角色管理 → 權限矩陣;結果看登入後的落點與側欄
- **帳號**:+tenant 改矩陣、+user 登入

### 劇本 14 — 管理範圍 vs 可見範圍

- **用哪一頁**:角色管理(建 / 換角色)+ 組織管理 / 使用者管理 / 角色管理(看樹根)+ 示範模組1 列表(看業務資料)
- **帳號**:+tenant 建角色與指派、被測的是 **+user**

### 劇本 17 — 擁有者保護

## E2E 怎麼跑(#378)

有 spec 的劇本**不必再人工走一次**,但 E2E **只在手動觸發時跑**(不進每個 PR 的 CI,理由見 TEST-05):

```bash
pnpm e2e                       # 本機全部(harness 會自己 build、起 Mongo / api / admin)
E2E_GREP="劇本 7" pnpm e2e     # 只跑某一條
gh workflow run e2e.yml --ref <分支> -f grep="劇本 7"   # CI(.github/workflows/e2e.yml)
```

harness、前置資料與寫法見 `apps/e2e/README.md` 與 `docs/standards/testing/testing.md` 的 TEST-11。
**「E2E」欄是「尚未」的劇本仍照本文件人工驗收**;補上 spec 的票要同時把這一欄改掉。

**額外一條(不在原 17 條內,#212)**:模組與權限頁 —— root 停用「示範模組2」→ +tenant 的側欄少一項;重新啟用只開這一個節點(停用父模組時整棵子樹視同停用)。
