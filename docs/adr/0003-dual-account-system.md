# 使用者與會員是兩套帳號體系:分表、分登入、分 token

## 帳號分離

admin 的使用者(User)與 front 的會員(Customer)分 collection、分登入端點。兩種 token 用 JWT 的 `aud` 欄位標記發給誰(admin 或 front),拿會員 token 打後台 API 會被拒絕,反之亦然。會員不進 RBAC:能力是固定集合 + 資料擁有權檢查;角色/權限體系只服務使用者。

## Token 與密碼

- 短效 access token(HS256,密鑰在 Secret Manager)+ 長效 refresh token(獨立 collection 存雜湊,支援輪替與「登出所有裝置」)。
- 簽章演算法不寫入資料庫;未來第三方需要驗證簽章時,改用 RS256+JWKS,只動設定。
- 密碼一律 argon2id(或 bcrypt)雜湊,禁明文與可逆加密。實作套件統一 **`@node-rs/argon2`**(官方 `argon2` 的 Windows 預編譯檔在 Node 20 載入即崩);seed 與 api 驗證必須同一套件。備案:`hash-wasm`(純 WASM、零原生依賴、慢 3–5 倍)。雜湊為標準 PHC 字串,跨實作可互驗。
- **登入不可枚舉帳號**:帳號不存在與密碼錯誤回同一個錯誤碼(`INVALID_CREDENTIALS`),**而且耗時相同** — 帳號不存在時也對一個假雜湊跑一次 argon2,否則「不存在秒回、存在慢一百毫秒」的差距就足以用碼表分辨帳號是否存在(時間側信道)。忘記密碼同理:Email 不存在也回「已寄出」。
- **登入相關錯誤碼的語意與前端對應**(`UNAUTHENTICATED` / `TOKEN_EXPIRED` / `FORBIDDEN` 等)正本在 `docs/standards/api/graphql-schema.md` GQL-04。
- **登入識別 = `account`**,users 與 customers 皆同;`email` 只用於信件流程定位(啟用信、忘記密碼),不作登入識別。兩者在**各自的表內唯一**(users 一個索引、customers 一個索引;使用者與會員是兩套帳號體系,跨表不互斥)。
- 第三方登入(Google 等)為預留:綁定存 `auth_identities`(固定從屬用欄位,不進核心關聯 — 見 docs/data-model.md 預留段),會員線開發時啟用。

## 所屬組織與角色授予

固定用語:**所屬組織** = 使用者屬於哪些組織(`org_user`);**角色授予** = 把角色授予使用者(`user_role`);**擁有組織** = 這個角色屬於哪個組織(`org_role`,每個角色只屬一個組織)。

- 使用者可同時屬於多個組織;token 只帶一個「當前組織」(AppBar 切換器選中的那個)。
- 每個角色只屬一個組織,所以查 `user_role` 就知道這筆授予來自哪個組織的角色,不需另外記組織。
- **被授予角色的資格**:使用者的所屬組織中,至少一個落在該角色擁有組織的子樹內。只在按下授予的當下檢查一次,之後不再檢查。下層組織的使用者可直接被授予上層組織的角色,不必先加入上層組織。
- 跨租戶授予一律禁止;要授予,先把使用者加入組織(另一個獨立操作)。
- 授予角色不會改變使用者的所屬組織,也不會改變他的資料可見範圍。
- **授予角色的防越權邊界見 ADR-0004「防越權與稽核」**(2026-09-21 整併,原本這裡有半段重複的規則)。
- 組織樹選取介面(組織下拉、使用者管理左樹、選擇所屬組織彈窗)一律以租戶頂層為根,可見範圍外或無權限的節點顯示但不可選。

## 權限解析(聯集模型)

- **功能面**:可進哪些頁 = 角色綁的模組取**聯集**(`role_module`);頁內哪些功能可用 = 角色綁的權限取**聯集**(`role_permission`)。完整查詢與判斷流程見 ADR-0011。
- **資料面**:可見範圍 = 所有所屬組織的聯集(租戶可見性開關 ON 時各自含下層),再由資料範圍規則在可見範圍內縮小(ADR-0008)。
- 當前組織不參與權限計算,只決定新資料寫入哪個組織(orgId)與業務模組的預設篩選。
- **v1 不做快取**:每次 request 由單一入口 `PermissionResolver.resolve(userId)` 現查(3 個索引查詢,毫秒級;後台流量小)。權限變更立即生效,無作廢時機、無多實例一致性問題。日後量測到熱點,在 resolver 內加程序內 LRU 即可,呼叫端不動。
- 已接受的副作用:角色的功能可操作持有者可見範圍內**其他分支**的資料;要更緊就用資料範圍規則收斂。

## 從組織移除使用者

- 移除所屬組織時**不自動解除任何角色授予**。確認彈窗以 radio 讓操作者選擇:(a) 全部保留 (b) 解除該組織擁有的角色 (c) 解除所有失去資格的角色 = 該組織擁有的 + 失去全部子樹支撐的(**預設**;字面上 (c) ⊇ (b),dry-run 逐筆回 `reasons`,兩種原因可同時成立)。例:使用者屬 A、A/B 兩組織,角色 R 由 A/B 擁有;移除 A/B → R 是「該組織擁有的」也是「失去子樹支撐的」;角色 S 由 A 擁有 → 使用者仍屬 A,S 不失去資格,(b)(c) 都不解除。
- 「失去資格」逐筆判斷被移除者持有的每個角色:該**角色**擁有組織的子樹 ∩ 該**使用者**移除後剩餘的所屬組織 = 空集合 ⟹ 失去資格(以 ancestors 一查即得)。後端 dry-run 逐筆列名;操作者的選擇與解除清單寫入 audit_logs。
- 保留的角色,其**模組與功能權限照常有效**;但資料依然是依照租戶可見性設定、所有所屬組織與資料範圍規則過濾後的範圍。
- UI 於相關列表標示「組織外」= 使用者的所屬組織皆不在該角色擁有組織的子樹內;畫面說明文案用白話「使用者不在該角色的所屬組織內」(樣式見 Figma)。
- **「使用者至少要有一個所屬組織」與組織的刪除前置檢查會互相咬住**(2026-09-23,#374):租戶頂層一定有擁有者這個成員,刪除前置的「無成員」因此永遠不過;而要移出擁有者又被本條與擁有者保護(ADR-0009)擋下。**開錯的租戶走「撤銷開通」,不走刪除** —— 那是一個根組織專屬的反向動作,連同它自己建出來的擁有者與角色副本一起收回,見 ADR-0009「撤銷開通」與 `docs/modules/org-manager.md`。

## 擁有組織 = 角色的管轄邊界(管理範圍,2026-09-19)

擁有組織原本已回答四個問題,現在多回答第五個;五個問題都由**同一棵子樹**回答,不另立範圍變數:

| 問題                               | 答案                                                          |
| ---------------------------------- | ------------------------------------------------------------- |
| 誰可以被授予這個角色               | 所屬組織落在擁有組織子樹內的人(本文「所屬組織與角色授予」)    |
| 移出所屬組織後還保不保這個角色     | 子樹 ∩ 剩餘所屬組織 = 空 ⟹ 失去資格(本文「從組織移除使用者」) |
| 「組織外」標示                     | 持有者的所屬組織皆不在子樹內                                  |
| 加入使用者的選人器候選             | 所屬組織在子樹內的人(ADR-0005)                                |
| **持有者在治理模組能操作哪些組織** | **擁有組織的整棵子樹**(= 管理範圍,CONTEXT.md)                 |

- 管理範圍 = 持有的啟用中角色各自的擁有組織子樹取**聯集**;持有超級管理員(擁有組織 = 根)= 全部。
- 「組織外」的授予功能照常有效(本文既有規則),所以管理範圍也照給;要收回就解除授予。
- 範圍不由持有者的所屬組織決定,也不受可見性開關影響(ADR-0005「管理範圍與可見範圍的分工」)。要給不同範圍就建不同角色:租戶管理員副本擁有組織 = 租戶頂層 → 管整個租戶;自建「南港店管理員」擁有組織 = 南港店 → 管南港店子樹;三家店沒有共同上層就建中間層組織或授三個角色。
- 角色管理頁「擁有組織」欄位下固定提示:「這個角色的持有者可以管理此組織與它底下的所有組織」;help.md 用同一句白話。
