# 權限模型:模組樹為命名空間、wildcard 同層、純加法、防越權下放

## 命名空間與 key

- 模組樹(= 側欄/頁面劃分,含隱藏頁)是權限的命名空間。
- **模組 key 累加父模組 key**:子模組 key = 父模組 key + `.` + 自己那段(如 `system.org-manager`、`demo.sub.sample-one`)。全樹皆然,治理模組也不例外;由種子的規約測試強制。
- 權限 key = 擁有模組 key + `.` + 動作(**動作恆為單段**,`*` 是唯一特殊動作),**全小寫 kebab-case、點分層,無例外**。例:`system.user-manager.edit`、`demo.sub.sample-one.edit-page.show-history`。
- key 切分:最後一段 = 動作,其餘 = 擁有模組 key。
- key 與顯示名分離;細至欄位顯示皆可為一筆權限。

## 歸屬

- 每筆權限屬於**恰好一個**模組:`permissions.moduleId` 直接欄位(固定從屬用欄位,ADR-0001)。
- **綁定原則:權限綁「它作為按鈕/欄位/跳窗/flag 所在的那一頁」**;跨頁共用的綁父模組。
- **反向歸屬不解析字串**:要知道權限屬於誰,看 moduleId;key 的前綴累加只服務可讀性。

## Wildcard(同層語意)

- **每個模組固定有一筆 `模組key.*`** — 群組、連結頁、隱藏頁、`api` 樹皆然;種子自動產生,規約測試強制「每模組恰一筆」。
- **`X.*` 只代表模組 X 自己這一層的全部權限(含未來新增)**,不涵蓋子模組;子模組的權限由子模組自己的 `*` 代表。
- 比對只有兩種:全字串精確比對;或「該權限的擁有模組 key + `.*`」在角色持有的集合中(一次查表,不掃字串前綴)。
- 儲存:角色對某模組「全給」時,`role_permission` 只存該模組的 `*` 一筆;取消同層其中一筆時,轉換為「刪 `*`、存剩餘個別筆」,其他模組不受影響。
- **收斂的基準必須是全樹**(操作者看得到的完整模組樹 = 全部 enabled 模組與權限),**不能是裁成操作者權限集的顯示樹,否則會擴權**:`*` 的語意是「這一層的每一筆都給了」,拿裁過的樹去收斂,會把「操作者只看得到 5 筆、勾滿這 5 筆」存成 `*`,而 `*` 連他沒有的那幾筆(含未來新增)一併授出(2026-09-20 / #203 寫測試時撞出;實作見 `docs/modules/role-manager.md`「矩陣的兩棵樹」)。
- 「整組全給」(子樹每個模組都全給)= 子樹每個模組各存一筆 `*`;矩陣上群組列的勾選狀態是**衍生**的(子樹全部有 `*` 才顯示勾),不另存群組層級的記錄。**以上只算「那棵樹上列得出權限」的模組**(2026-09-22,#363):餵進來的樹(尤其是顯示樹)若把某模組的 `*` 列剪掉了,整組全給就不替它生 `*`、群組列也不要求它 —— 生出來的那一筆授不出去,只會被下面的防越權擋下。
- 解析規則:聯集、純加法、沒有 deny。
- **超級管理員例外**:持有 isSystem 超級管理員角色者,解析時**直接全權放行(bypass)**,不靠權限記錄表示 — 資料庫中不存在全域 `*` 權限(權限必屬某模組)。

## 頁面(模組)的進入權

- **可進 = 角色綁了那個模組**(`role_module` 關聯):模組即頁面;route 必須明確,不可有 `*`。
- 權限矩陣 UI 保證樹完整:勾下層模組必連動勾上層;有子孫被勾的上層為「勾選且不可取消」。
- 隱藏頁(sidebarType=hidden **且有 route**)key 一律以 `-page` 結尾;權限動作禁用 `-page` 結尾 — 模組 key 與權限 key 永不同字串。**無 route 的隱藏節點不是頁面、只是權限容器**(`api` 模組樹、`system.org-manager.tenant-ops` 這類根組織專屬動作的容器),不受 `-page` 規則約束,`me.modules` 對它們回 `route: null`(2026-09-19 改,原本只寫 `api` 樹例外)。
- 隱藏頁可擁有權限(例:編輯頁的變更歷程區塊),也有自己的 `*`。
- 登入後的完整查詢與判斷鏈路見 ADR-0011。

## API 權限

預設**重用頁面權限 key**(controller 標註),避免頁面/端點雙重記帳;僅無對應頁面的純 API 能力放進隱藏的 `api` 模組樹。

## 防越權與稽核

防越權分兩層,各守各的(2026-09-21 把原本散在 ADR-0003「所屬組織與角色授予」的授予層規則整併於此):

- **權限上限 — 權限矩陣的 subset-only**:操作者只能授出自身有效權限集的子集:持有 `X.*` 可授出 X 這層的任何權限與 `X.*`;子模組的 `*` 要自己持有才能授出。**模組勾選同理 — 只能勾自己也有路由的模組**。
- **粗篩 — 授予角色時看擁有組織**:「授予角色」(使用者頁的「指派角色」與角色頁的「分配使用者」是同一件事的兩個入口)的判準是**角色的擁有組織在操作者的管理範圍內**,不在 → `ROLE_OUT_OF_REACH`。它只是粗篩,真正的上限由上一條封頂。持超級管理員角色者 bypass(本文「超級管理員例外」),否則根組織無法把租戶角色授予任何人。
  - **2026-09-20 / #203 + #211 改**:原判準是「只能給自己持有的角色」,它會讓「自己建了一個角色卻不持有它 → 永遠授不出去」(#201 的驗收劇本就是這樣建「南港店管理員」再授人),而且 `grantRoleUsers` 與 `assignUserRoles` 兩套判準會讓同一個授予**從角色頁做得到、從使用者頁做不到**。兩邊已統一為本條;模組側正本見 `docs/modules/user-manager.md`「防越權」。
- 日後操作者失去權限,已授出的不自動回收。
- 授權相關動作寫入 `audit_logs`(誰、何時、動作、對象、前後值),**由執行動作的模組層(角色管理、使用者管理等)負責寫入**;RelationService 只管關聯本身,不記稽核。v1 只記授權變更,不記一般 CRUD。

## 欄位級權限(2026-09-22 / #318 定;先例 `demo.sub.sample-one` 的 `internalNote`)

權限細至欄位(本文開頭「細至欄位顯示皆可為一筆權限」)時,那筆權限**綁欄位所在的那一頁**(「歸屬」節),讀寫各有一種擋法:

- **讀**:沒有該權限時 api **不把欄位放進回傳物件**,GraphQL 因此序列化成 `null`(輸出端沒有「欄位缺席」這回事,GQL-06)。列表與單筆一致。「沒權限」與「沒填」在值上長得一樣,所以**前端依自己的權限集決定渲不渲染**,不要拿值去猜。
- **寫**:input 裡出現一個操作者不能寫的欄位(含送 `null` 清空)→ `FORBIDDEN` + `reason FIELD_FORBIDDEN`(GQL-04)。端點本身可以用,擋的是那一欄。

**擋了讀,就要把所有繞道一起擋掉** —— 否則投影白做。兩條一起適用於每個受欄位級權限保護的欄位:

- **稽核歷程一律記 `"[redacted]"`,不記內容**:`audit_logs` 的 `before` / `after` 只放有變的欄位,而受權限欄的值**一律換成 `"[redacted]"`**(常數 `REDACTED`)。否則「沒有讀的權限、卻有看變更歷程的權限」的人可以從歷程把它讀出來。有沒有變仍然記得到(欄位出現在 diff 裡),變成什麼記不到。
- **關鍵字搜尋不比對受權限欄**:清單的 `keyword` 只比對**不受保護的**欄位(示範模組1 是 `name` / `note`)。比對了就等於做出一個 oracle —— 打一段字看哪幾筆被篩出來,值就被猜出來了。即使操作者**有**該欄位的讀權限也一樣不比對,因為「搜尋結果依操作者而不同」會讓分頁與 `totalCount` 對不起來,規則要一句話講得完。

這兩條屬於「加一個欄位級權限欄」的**固定配套**:新增這種欄位時,mapper 的投影、歷程的 redact、`keyword` 的比對欄位三處一起改,並在 `docs/modules/<key>.md` 寫明。scaffold 產模組時照抄這個形狀(`docs/agents/module-scaffold.md`)。

## 角色種類與可改動範圍(2026-09-21 / #261)

subset-only 管「授出什麼」,本節管「這個角色本身動得了什麼」。三種角色的判準互斥,由上往下取第一個成立者:

| 角色種類                             | 判準                           | 改名 / 描述 | 權限矩陣                                                             | 停用                                | 刪除       | 分配使用者 |
| ------------------------------------ | ------------------------------ | ----------- | -------------------------------------------------------------------- | ----------------------------------- | ---------- | ---------- |
| **種子**(超級管理員、租戶管理員模板) | `isSystem`(seed 一併補齊,#246) | 不可        | 唯讀                                                                 | 不可                                | 不可       | 可         |
| **預設角色**(租戶副本)               | `settings.templateKey`         | 租戶可      | **上限 = 內建租戶管理員模板** — root:模板範圍內放寬 / 收窄;租戶:收窄 | 只有 root(自鎖保護)                 | 不可       | 可         |
| **自建角色**                         | 其餘                           | 可          | 依 subset-only                                                       | 可,但不可停用操作者自己正持有的角色 | 無授予時可 | 可         |

- **預設角色的天花板**(2026-09-21 / #283):矩陣上限是**系統內建「租戶管理員」模板角色目前的授予**(seed = 所有非根組織專屬模組各一筆 `*`,不含租戶作業、模組與權限、資料範圍;正本 `apps/db-migrator/seeds/role-bindings.ts`)。**root 也不例外** — 平台方要替租戶開一個模板沒有的模組,先把它加進模板(走 code + PR,ADR-0002),而不是逐個租戶偷加。超出 → `ROLE_OUT_OF_REACH` + `extensions.reason = TEMPLATE_CEILING`。天花板讀的是模板**現在**的綁定,不是開通當下的快照。
- **自鎖保護**:上表「不可停用自己正持有的角色」與模組側「不可停用 `system.module-manager` 子樹或其權限」是同一條原則 — **不讓任何人把自己關在門外**;兩者都是不可逆才禁,可逆的就不禁。
- 種子角色的矩陣隨版本更新(ADR-0002:結構異動走 code + PR),所以唯讀而非「暫時不給改」。
- 判準、錯誤碼與前端落點見 `docs/modules/role-manager.md`「角色種類與可改動範圍」。
