# 多租戶隔離:orgId + BaseRepository 自動過濾 + ancestors 樹

## 資料隔離機制

- 所有租戶資料 collection 都掛 `orgId`;複合索引以 orgId 開頭。
- 所有查詢必經共用層 **BaseRepository**(禁用裸 `Model.find`,由型別感知 ESLint 規則 `@repo/no-raw-model-query` 強制):內部以 Mongoose plugin 自動把「orgId ∈ 操作者可見組織」加進查詢條件 — 個別功能不自己寫這條過濾,也繞不過。
- **資料層三類 collection**(詞條見 CONTEXT.md「資料層」):租戶資料(掛 tenantScope plugin,自動過濾)、全域資料(不掛,不過濾)、關聯歸屬資料(users / roles:沒有 orgId,由模組經 org_user / org_role 查關聯後再查本表,資料層**不**自動保護)。哪些 schema 掛了 plugin 由測試鎖定。
- **操作者上下文**是 BaseRepository 每個方法的第一參數(操作者 id、當前組織、可見範圍)。**沒帶上下文的查詢直接拋錯(fail-closed)**,不會靜默回傳全部;租戶條件以 `$and` 追加,呼叫端自己的條件只能再收窄。
- 根組織的可見範圍以 `"all"` 表示(不列舉組織 id),plugin 遇到即不加過濾。
- 寫入保護:`create` 自動寫入當前組織、不可寫入可見範圍外;`updateById` 不得變更 `orgId`(否則可把資料搬進別的租戶)與建立資訊 `createdBy` / `createdAt`。搬移組織若有需求,是獨立且明確的操作。
- `audit_logs` 視為租戶資料(orgId 必填);根組織的操作記在根組織名下。
- **已知限制**:Mongoose `populate()` 的子查詢不帶上下文,對租戶資料會拋錯 — 現階段關聯資料分兩次查;將來由 BaseRepository 轉傳上下文(dis.md #28)。
- 組織與模組樹採物化路徑:每份文件存 `ancestors` 祖先 id 陣列;子樹查詢一句 `find({ ancestors: X })` 完成;搬移節點時批次更新子孫。

## 可見範圍

- 「使用者可見下層組織資料」開關掛在**租戶頂層**(根組織的直接子組織)的 `settings`,套用整棵子樹;不做逐層自決(嵌套矛盾難解)。根組織(平台營運者)預設可見全部。
- 開關在 `settings` 裡的鍵名與值:**`settings.visibility`**,列舉 `"own"`(使用者只看得到自己所屬組織的資料)或 `"subtree"`(所屬組織連同其整棵下層的資料);**沒有設定時視為 `"own"`**(保守預設,租戶要開才開)。只有租戶頂層的這個值有效,下層組織不看自己的。
- 可見範圍 = 所有所屬組織的聯集(開關 ON 時各自含其下層)。
- 頁面預設顯示範圍是**各模組頁面自己寫死的慣例**,不是設定:**治理模組(組織 / 使用者 / 角色管理)的上限是管理範圍**(見下節),一律攤開整個管理範圍,組織樹只是篩選器;**業務模組的上限是可見範圍**,慣例上預設以當前組織篩選,個別模組需求不同就在自己頁面改。新資料一律寫入當前組織。

## 可見性開關與角色授予的關係

- 開關只影響**業務資料**:業務 collection 的清單自動與操作者的可見組織取交集(由 BaseRepository 加上);治理類 collection(`orgs`、`users`、`roles`、`core_relationships`)改吃管理範圍(下節)。
- 開關**不影響**被授予角色的資格:資格恆以擁有組織子樹判定(ADR-0003);開關切換不觸發角色授予的重算或回收。
- 加入使用者選人器的候選範圍 = 所屬組織落在**該角色擁有組織或其下層**的使用者 — 由角色決定,與操作者是誰無關;操作者實際看得到其中哪些人,再與操作者的可見範圍取交集。

## 其他

- UI 提示文字用白話(如「或其下層組織」),不用內部術語。
- front 會員註冊預設歸屬根組織,底座允許指定其他組織。
- 欄位管理:類別(母檔)為全域種子、租戶不可自訂;選項(子檔)帶可空 `orgId` — null 為全域種子、有值為租戶自訂,下拉載入時合併(`$or`);選項含 `order` 與啟用狀態(下架不刪,舊資料仍引用)。

## 管理範圍與可見範圍的分工(2026-09-19 定案,第 3 段驗收發現)

第 3 段把治理頁也綁在可見範圍上,結果租戶管理員在開關為 `own` 時只看得到自己所屬的幾個組織,管不了自己的租戶。改為兩個範圍各管各的:

| 範圍         | 誰決定                                         | 管什麼                                              | 程式            |
| ------------ | ---------------------------------------------- | --------------------------------------------------- | --------------- |
| **管理範圍** | 持有的啟用中角色之擁有組織子樹的聯集(ADR-0003) | 治理模組:組織樹的根、使用者清單、角色候選、搬移候選 | `managedOrgIds` |
| **可見範圍** | 所屬組織 + 租戶頂層的可見性開關                | 業務資料看多少(資料範圍規則在其中再縮小)            | `visibleOrgIds` |

- 操作者上下文同時帶兩個集合;BaseRepository 依 collection 類別選用:治理類吃管理範圍、業務類吃可見範圍(CONTEXT.md「資料層」三類)。
- **上下文裡是四個不同的集合,不可互相代用**(2026-09-20 / #205 執行資料範圍時補上後兩個):

  | 集合            | 內容                                                            | 誰用                                                       |
  | --------------- | --------------------------------------------------------------- | ---------------------------------------------------------- |
  | `managedOrgIds` | 啟用中角色的擁有組織子樹聯集                                    | 治理類 collection 的過濾、角色 / 使用者候選                |
  | `visibleOrgIds` | 所屬組織(開關 ON 時各自含下層)                                  | 業務類 collection 的租戶保底                               |
  | `memberOrgIds`  | **所屬組織的直接關聯**(`org_user`),**不含**可見性開關展開的下層 | 資料範圍的套用對象「指定組織」、動態值【操作者的所屬組織】 |
  | `roleIds`       | 持有的**啟用中**角色                                            | 資料範圍的套用對象「指定角色」(停用角色後規則立刻不再命中) |

  資料範圍的執行只吃後兩個 — 「所屬組織」在 ADR-0008 指的是 `memberOrgIds`,**不是**可見範圍也不是管理範圍。語意正本見 `docs/modules/data-scope.md`「執行面的回傳語意」。

- **開關由誰設**:租戶頂層的擁有者 / 持有 `system.org-manager.set-visibility` 的租戶使用者(它是租戶自己的資料政策)+ 根組織;只能設自己租戶的頂層。此權限從根組織專屬的 `tenant-ops` 搬到組織管理層,租戶管理員模板自動取得。
- 開關**不影響**治理頁、角色資格、管理範圍;切換不觸發任何重算。
- 租戶頂層本身的停用 / 刪除 / 搬移**只有根組織**可做(ADR-0009);租戶內的人只能對子組織做。
