# 設定由程式碼交付,業務資料保留在各環境

> 現況說明見 `docs/concepts/data-layer-and-isolation.md`「種子資料與遷移」。

## 決策

- 設定與業務資料分開管理:
  - **普通種子資料**(模組、權限、種子角色、欄位管理、資料目標):程式碼定義,以穩定 `key` 在各環境冪等 upsert;id 各環境各自生成。
  - **受管定義**:明確登記的共用表單與共用流程,使用同一套 TypeScript seed 契約,經既有設計服務發布或退役,不直接 upsert 版本內容。
  - **業務資料**(帳號、食譜等):不跨環境搬移。重現正式環境問題用整庫 dump / restore,還原後補跑 seed。
- 不將其他環境的部分業務資料或資料庫 ID 匯入既有環境。設定以穩定 key 解析當地引用;同一環境內的資料轉換交給明確 migration。
- 普通種子記錄以 `isSystem` 保護:不可刪、不可改 key,只有 seed 能維護。
- **普通 seed 以 key 認養人建的同一筆**:同一類資料允許人在畫面建(`isSystem: false`,如 root 在欄位管理新增的類別)時,seed 宣告同一個 key 就把那一筆轉成種子 —— `isSystem` 改 true、宣告的欄位以 seed 為準、`_id` 不動(引用它的資料照舊)。人建時沒有種子 key 的,由 `adoptBy` 指定對應方式。未宣告資料不動;結果區分新增、更新、認養與未變。
- 執行手段是獨立的 `apps/db-migrator`:migrate-mongo 管一次性遷移,薄 runner 管冪等種子。不部署、不常駐、不新開資料庫。
- 部署 api 成功後依序跑 `migrate` → `seed`。build 不碰 DB;server 啟動時不跑。
- 種子欄位分兩種:**每次都 seed**(預設)與**初始 seed 值**(欄位存在就不覆寫,只補從未寫過的欄位)。
- 授權關聯維持只補不刪:從 seed 移除角色與模組/權限的綁定宣告,不自動撤銷資料庫既有授權;要撤銷時另作明確的權限管理操作。
- seed 不分環境,三環境跑同一份宣告。
- 底座與專案分別維護 `seeds/base/`、`seeds/project/`,只由 `seeds/registry.ts` 組裝。底座維護契約、組裝與執行器;專案提供自己的宣告及根組織、模組初值,不以同 key 覆蓋底座宣告。
- 兩方模組合併後一次推導權限、資料目標與租戶管理員模板。來源碰撞、引用或循環檢查失敗時,整批停止且不寫入。
- 普通 seed 以原生 mongodb driver 寫文件,不 import api 的 schema。版本定義透過 API 的受控 CLI 呼叫原設計服務,沿用真實操作者、權限、發布與稽核;app 之間不互相 import。
- key 對 production 跑過 seed 就不再改;改 key = 新種一筆,要配 cleanup migration。
- root 初始帳號從環境變數建立,只在不存在時建。

### 受管定義

同一專案交付相同定義內容,不要求各環境 ID 或歷史版號相同。宣告以 `(kind, key, revision)` 識別,同 revision 不可改內容;安裝紀錄保存該環境的版本映射與續跑狀態。未登記的共用定義及租戶客製、fork 由各環境獨立管理,人員、分派與綁定不隨定義交付。

初次納管只採納內容完全相同的共用發布版,保留原 ID 與歷史。受管改版先核對現場;未預期草稿、發布中斷、版本或名稱漂移均停止,不強制覆蓋。本次安裝自己的中斷則依預配置 ID 接續,完成與重跑都核對實體。移除宣告只停止管理;退役需明確宣告,重新發布需新 revision 與版號。

## 理由

- 設定描述的是內容,各環境的人員、租戶與歷史各自存在;以 key 和版本映射建立當地引用,不必同步資料庫 ID。
- 表單與流程的已發布版本會被提交、修訂及在途流程引用。沿原生命週期建立新版才能保留這些引用,一般 upsert 會破壞凍結內容與發布檢查。
- 初始 seed 值的欄位(如 `enabled`、模組的 `icon` 與 `settings`、根組織的 `name`、`description` 與 `settings`)是給人在畫面上管的值,seed 不該每次翻回去;只補「從未寫過的欄位」,後來才加進宣告的初值欄位才落得了地。根組織名稱與描述在新專案建立時先指定 seed 初值,一般部署保留 UI 修改(描述清空也保留),完整清庫還原才重建成該專案的宣告值。
- 認養而不是另建一筆:人建的那一筆可能已被表單定義或業務資料引用,另建會讓同一個 key 出現兩筆、引用對到舊的;`_id` 不動,引用就不必搬。
- 不在 server 啟動時跑:Cloud Run 冷啟要快,也避免多實例併發寫。
- seed 不 import api:STRUCT-01 禁 app 互相 import,且 BaseRepository 對沒有操作者上下文的查詢一律拋錯。
- root 帳號只建不改:部署不能重設密碼。
- 分來源讓底座更新與專案設定各有固定修改位置;共同組裝才能把專案子模組算入完整模組樹與模板,避免兩邊各自推導而漏授權或重複宣告。一般 seed 的型別、保留欄位及認養機制共用,不因分區另建一套格式。

## 取捨

- 欄位形狀存在兩處(api schema 與 seed),schema 改了 seed 要跟;索引測試抓不到欄位漂移。漂移變嚴重再抽共用型別套件(待辦見 `docs/tmp/dis.md` 搜「db-schemas」)。
- migrations 維持 `.js`(migrate-mongo 的載入器);seed 以 tsx 直跑 TypeScript。
- 示範模組初建啟用,production 也允許示範資料;模組開關與租戶分配由人員維護,seed 不自動停用或撤銷分配。

## 還原(reset)

- `apps/db-migrator` 的第三支指令,驗收重測用,**只給 dev / staging**。
- 兩種模式:`full`(drop → migrate → seed,人調過的初始值一併回到宣告值)與 `data`(只刪人建的資料再 seed,人調過的初始值保留)。
- `data` 模式「seed 管 / 人建」的判準只有一個來源:registry 宣告的識別鍵。不看 `isSystem`,也不寫死 collection 清單;不在 registry 的 collection 整表清空。例:root 在畫面建的欄位類別,key 不在宣告清單裡就算人建的、一起刪;key 已宣告的那一筆留著,由同一次執行的 seed 認養。
- production 永遠拒絕,沒有旗標能打開。

**理由**:驗收要能回到乾淨狀態重測;判準只看 registry,日後新增的業務表自動被清,不必回頭改 reset;`data` 模式能保留人調的開關,正是「初始 seed 值」機制的直接結果,seed 端不必為 reset 做任何事。

## 影響

- 新增設定類資料 = 加宣告檔 + 登記 registry。
- 改種子欄位的形狀要同步 seed 宣告。
- reset 的用法與 workflow 見 `docs/deployment.md`「資料庫還原(reset)」。
