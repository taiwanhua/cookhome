本文件保存底座抽離的已定案要求、目前交付範圍、待決設計與驗證證據。Claude、Codex 或人員只靠 repo 與 issue/PR 即可接手,不需要任何工具的本機對話或交接目錄。現有實作以程式、`docs/concepts/` 與 ADR 為準;本文件的後續工作包不代表已實作或已獲准開工。

## 已定案的要求

### Repo、所有權與客製

- 底座與每個引用專案各有獨立 repo;CookHome 是第一個引用專案,保留自己的品牌與業務。底座名稱尚未決定,不以同一 repo 的長期分支管理各專案。
- 新專案從底座正式版本起步並保留共同 Git 歷史;固定帶完整 front、admin、api,暫時不用的 app 也保留。具體建立命令尚待設計,不能直接把 GitHub Template 按鈕當作共同歷史的保證。
- 必須分清底座維護與專案擴充。底座/專案內容從起點分資料夾存放,各自維護模組、路由與設定登記,由固定組裝入口組合。分工原則已定,確切路徑與介面尚未定案。
- RBAC、租戶隔離等核心由底座維護;專案需求透過設定及擴充滿足,核心修正先回底座評估。表單引擎、審核流程、申請中心及預設畫面屬底座;表單、流程定義與業務資料由專案/租戶維護。
- 治理頁允許專案另存客製版並登記替換,仍使用底座受保護介面。底座原版保留並持續更新,不可直接覆寫客製頁;專案負責客製頁相容性與測試,升級須特別檢查。
- 前台畫面、版型與風格由專案設計;底座保留 app 骨架與共用能力。不要求前台接入後台主題或 `AppThemeProvider`。
- 示範程式與藍本由底座維護,業務另建模組。正式環境可灌示範資料,保留模組初建啟用的現行行為;開關與租戶分配由人員操作維護,不新增強制停用或自動排除模板策略。

### 品牌、初始化與資料

- 底座盡量去品牌化;共用文件、skills、註解不寫死引用專案名稱。共用名詞由 `CONTEXT.md` 管理,專案品牌、客製頁、業務及專案文件有自己的來源。
- 先做完整初始化盤點,再製作引導 skill。所有新專案需獨立設定的項目都納入:品牌與後台主題、repo/看板、開發工具、資料庫、環境變數、Cloud Run、其他雲端資源、寄信、網域及 Figma。skill 引導使用者提供輸入,分開記錄已提供、已建立、已驗證;只改檔案不代表資源可用。
- 初始化與升級分開。升級只更新底座擁有的定義與允許欄位,保留專案設定、帳號、組織及業務資料;必要資料變更走明確且經驗證的 migration,不以 reset 取代升級。
- 新專案先指定根組織 seed 名稱與描述。UI 改值或清空描述後,一般部署保留;data reset 保留這些初始值欄位,full reset 依該專案 seed 重建。完整還原不是備份復原,現有 production reset 限制維持。API 清空缺口由本批修正票驗收。
- 維持同層 wildcard 涵蓋新增動作;只持個別權限的角色不自動取得,全新模組另行授權。升級報告列受影響角色與新增能力,區分種子模板與既有租戶副本。
- seed 授權關聯維持只補不刪:移除宣告停止補建,不自動撤銷 DB 既有授權。實際撤銷由人員管理操作或另行明確授權的 migration 處理。

### 更新、回收與設計同步

- 向下同步以正式版本為單位,不隨每次 main commit 升級。讓專案容易持續升級優先,backport 僅作例外,不預設長期多版本支援線。
- 底座正式發布後,由 agent 自動準備各引用專案升級 PR:建立分支、分析影響、整合、修正相容性並測試;不確定行為列待決,由使用者審查並決定合併、發布。這是待建機制,目前未啟用。
- 每次引用專案 PR,由 agent 主動辨識底座改動與共用價值,提出回收建議;使用者決定是否投入整理及納入底座,不自動接受回收。
- Figma 也屬完整同步範圍:底座 Library 發布 → 專案接受更新 → 補套專案品牌 → 驗元件連結、品牌遺漏與客製內容。新增實例、切換變體亦須套用/檢查,不能只同步 Git 就宣稱完成。

## 完整交付的判斷

目前可交付的是共同文件與根組織修正這一批;底座抽離仍在規劃。後續只有當新專案建立、正式版本升級、專案改良回收與 Figma 同步都能依共同文件重現,且保留專案客製與資料,才能宣稱底座跨專案維護機制完成。所有驗收需附實際分支/commit、命令或操作結果與限制,不能只以盤點表或 skill 已存在代替。
